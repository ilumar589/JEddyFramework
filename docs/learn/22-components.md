# 22. Components and behaviours: a gameplay API generated at compile time

*Milestone M22 (2026-10-12). Read [01 Architecture](01-architecture.md) (entities, SoA, the job
system), [12 Fast Java](12-java-performance.md) (allocation, the JIT) and [14 The level
editor](14-editor.md) (the level format, the inspector) first. Lesson
[L03 Data layout](lessons/03-data-layout.md) goes deeper into the cache arithmetic this chapter
rests on.*

## 1. Goal and result

Before M22, every gameplay system in the demo was a bespoke set of arrays wired by hand:
`Enemies` had seventeen of them (`state`, `timer`, `cooldown`, `homeX`, ...), `Spells` had
eleven, and nothing outside those classes knew what a skeleton *was* beyond a transform and a
renderable. The editor could not show one, the save system (M16) would have to learn each class
by hand, and adding a system meant adding arrays, loops and growth code again.

Unity answers this with `MonoBehaviour`: subclass, override `Update()`, drag the component onto
an object. Jeddy answers it with the same *surface* and a different *engine*: a component is a
plain Java `record`, a behaviour is a `static` method, and an **annotation processor** turns
them into stores, views, loops and a registry at compile time. What runs is static calls over
primitive arrays; nothing reflects, nothing is virtual, nothing allocates per frame. This is what
the owner asked for on 2026-10-12: "a unified API for basic behaviour, generated by an
annotation processor to generate efficient code, not an inheritance model".

What you can write now, from the demo:

```java
// samples/iso-demo/src/main/java/dev/jeddy/samples/iso/Sight.java
@Component(doc = "Seen by the party, and hidden in the world")
public record Sight(@Default("true") boolean visible, boolean hidden) {}
```

```java
// samples/iso-demo/src/main/java/dev/jeddy/samples/iso/SkeletonAi.java
@OnFixedUpdate(stage = 1)
@Parallel(grain = 32)
public static void see(
        MonsterView m,
        MindView mind,
        SightMut sight,
        @ThreadSafe Visibility vis,
        @ThreadSafe Crowd crowd) {
    boolean v =
            mind.state() != MonsterState.DEAD
                    && vis.isVisible(crowd.x(m.agent()), crowd.z(m.agent()));
    sight.setVisible(v);
}
```

and, with `@Components(name = "CryptGame")` on the package, the game calls
`game.fixedUpdateStage(1, dt)` and 300 skeletons are tested against the fog-of-war grid on the
job system. The result of the milestone:

- `modules/components`: the annotations, `Store` (a sparse set with one array per column),
  `View`, the snapshot I/O (into `core.io.ByteWriter`, since M16) and the level-row loader.
- `tools/component-processor`: the processor; JDK only.
- The demo's skeletons and fireballs are five records and two behaviour classes; the perf
  capture is still at 0 B per frame, and a new row measures the behaviours.
- The editor's inspector shows an object's components from the schema the processor writes,
  the `.jlevel` carries their rows (format version 2), the cooker validates them, and
  `CryptLevel.PLACEMENT_CHEST` names what the editor placed.
- Every store writes and reads itself, which is the data layer M16 will save.

## 2. Background: the data layout and why the flyweight is free

### 2.1 Struct of arrays and the sparse set

An entity with a `Mind` component needs seven numbers (a state, three timers, a home position).
Put them in an object and 300 skeletons are 300 objects scattered over the heap; a tick that
reads every `timer` touches 300 cache lines of 64 bytes to use four bytes from each. Put each
field in its own array and the same tick reads $300 \times 4 = 1200$ bytes, nineteen lines,
sequentially, which the prefetcher sees coming. That is the whole argument for **struct of
arrays** (SoA, chapter 01 §7.1) and it is the layout the generated store uses: `MindStore` is
seven arrays and nothing else.

Which row is entity $e$'s? A **sparse set** (`core.collections.SparseSet`, D4) keeps two arrays:
`sparse[index(e)]` gives the dense row or −1, and `dense[row]` gives the index back. Membership
is one load and one compare, $O(1)$; adding appends a row; removing moves the last row into the
hole and fixes both arrays, also $O(1)$. The price is that rows are not stable: a removal
renumbers one entity. The generated `moveRow` does the swap for every column:

```java
// build/generated/.../MindStore.java (generated)
@Override
protected void moveRow(int from, int to) {
    state[to] = state[from];
    timer[to] = timer[from];
    cooldown[to] = cooldown[from];
    corpse[to] = corpse[from];
    homeX[to] = homeX[from];
    homeY[to] = homeY[from];
    homeZ[to] = homeZ[from];
}
```

### 2.2 The query and its cost

A behaviour with required components $C_1 \dots C_k$ runs for the entities that have all of
them. The generated loop walks the *smallest* store and tests membership in the others: for a
driver of $n$ rows that is $n$ iterations with $k$ sparse lookups each (the driver's own lookup
included, which keeps the loop one piece of code whichever store is smallest). With `Monster`,
`Mind`, `Sight` and `Flash` all on the same 300 entities that is 300 iterations and 1200 lookups,
each a load and a compare: a few microseconds. An archetype ECS avoids the lookups by storing
entities with the same component set together; it buys that with chunk management and
structural-change deferral that this engine does not need at these sizes (D107).

### 2.3 Walking backwards

A behaviour may despawn the entity it is visiting (the reaper in the tests; `Fireballs.fly` when
an explosion has faded). Removal swaps the last row into the hole. Walking **forwards**, the row
that moved in would be skipped this tick; walking **backwards**, the last row has already been
visited, so moving it into the current slot is harmless, and components added during the loop
land past the start index and run next tick. The generated loop therefore counts down, and
guards against the size shrinking under it:

```java
// build/generated/.../CryptGame.java (generated)
private void SkeletonAi_think_loop() {
    Store drive = Store.smaller(Store.smaller(Store.smaller(monster, mind), sight), flash);
    float dt = this.dt;
    for (int i = drive.size() - 1; i >= 0; i--) {
        if (i >= drive.size()) {
            continue; // rows went away under the loop
        }
        int e = drive.entityAt(i);
        int r0 = monster.indexOf(e);
        if (r0 < 0) {
            continue;
        }
        // ... r1, r2, r3 likewise ...
        SkeletonAi_think_v0.at(monster, r0);
        SkeletonAi_think_v1.at(mind, r1);
        SkeletonAi_think_v2.at(sight, r2);
        SkeletonAi_think_v3.at(flash, r3);
        dev.jeddy.samples.iso.SkeletonAi.think(SkeletonAi_think_v0, SkeletonAi_think_v1,
                SkeletonAi_think_v2, SkeletonAi_think_v3, dt, e, enemies, party, crowd,
                animator, agentSync, level, rng, world);
    }
}
```

The one anomaly left: removing *another*, not yet visited entity moves an already visited row
into its place, which then runs twice this tick. Gameplay tolerates that; a behaviour that
cannot defers the removal to a later stage.

### 2.4 Why `h.current()` costs nothing

`MindView.timer()` is `return store.timer[row];` — a field load (`store`), a field load
(`timer`), a field load (`row`), an array load. The behaviour calls it through a parameter of
static type `MindView`; the only subclass is `MindMut`, the method is `final`, so the call site
is monomorphic and C2 inlines it. After inlining, the loads of `store` and `row` that follow
`at(store, row)` are replaced by the values just stored (load elimination): they live in registers,
and the body is the same `iaload`/`iastore` sequence a hand-written column loop produces. The view
itself stays an object (a registry field), so its two field stores remain; stores are cheap. The JMH benchmark
(`ComponentsBench`, §6) measures it: over 10,000 entities one tick costs **4.8 µs** as a
hand-written SoA loop, **6.5 µs** through the generated loop, and **142 µs** as an object per
entity with a virtual `update()` — the `MonoBehaviour` shape — whose call site is megamorphic,
since three subclasses already defeat inline caching (CI's smoke run, 2026-10-12). In the benchmark
the objects are allocated in one loop and sit close together, so that gap is mostly the
megamorphic call; in a game, where objects are allocated over time and scattered, cache misses
add to it (lesson L03 §2 measures both). The 1.7 µs between the first two is not the view: it is
the *query*, a sixth of a nanosecond a row for the entity indirection (`entityAt`), the size
guard and the view's two field stores; a loop with several required stores looks the entity up
in each of them (two loads and a compare per store, the driving store included). The body itself compiles to the same instructions. Against the object
shape the generated loop is twenty times faster, and the gap grows with the heap: scattered
objects miss the cache more the more there are.

The benchmark earned its place on the first run: the generated loop measured **22 µs**, five
times the hand-written one, because the driving store looked its own entity up again (`indexOf`
on the store the loop was already walking: a dependent chain of three loads per row). Skipping
that lookup when one store drives — its row *is* the loop index — brought it to 6.5. Measure,
then read the generated code.

### 2.5 Parallel behaviours and the dependency rule

`@Parallel` turns a loop into a `JobKernel` over ranges of the driving store with one set of
views per job thread, and consecutive parallel behaviours of a stage into one `JobGraph`
(chapter 01 §14.1). The graph's edges come from what the parameters declare: a `Mut` is a write,
a `View` (and `@Optional`, and `@Without`) a read. Behaviour $B$ depends on an earlier $A$ when

$$W_A \cap (R_B \cup W_B) \neq \emptyset \quad\text{or}\quad R_A \cap W_B \neq \emptyset,$$

the read-after-write, write-after-write and write-after-read hazards of a CPU pipeline, applied
to components. Two behaviours that write disjoint components run concurrently even over the
same entities, because each only touches its own entity's row through its own views. A
behaviour that writes `Position` after one that reads it waits. Races are therefore prevented by
construction rather than detected at run time (D107); the price is that a parallel behaviour
must not change structure and may only take singletons its author marks `@ThreadSafe` at the
parameter.

**What the measurement said.** The demo's visibility test (`see`) is parallel over 300 rows.
On the 2-core container the perf row *Component behaviours per tick* read 0.14 ms average on
the job system and **0.11 ms inline** (`--inline-behaviours`). The work is 300 grid lookups of
some 50 ns, 15 µs in all; dispatching a job graph costs tens of microseconds (fences, wake-ups,
the wait). Parallelism has a fixed cost, and a behaviour pays for it only when

$$\text{rows} \times \text{ns per row} \gg \text{dispatch cost} \approx 20\text{–}50\ \mu s,$$

which 300 cheap rows do not satisfy. The demo keeps `see` parallel as the worked example and
says so; on the owner's 8-core desktop the numbers differ, and `--inline-behaviours` is there to
compare. The lesson is the rule, not the verdict: measure, and parallelize work, not loops.

### 2.6 Stages

One `fixedUpdate(dt)` call cannot interleave with systems that are not components: the demo's
tick is *think → party → crowd → sync → collision → fireballs → fog → visibility*, and the
crowd and the fog are not behaviours. `@OnFixedUpdate(stage = n)` groups behaviours into
stages; `fixedUpdate(dt)` runs them all in order and `fixedUpdateStage(n, dt)` runs one, so the
demo calls stage 0 where `enemies.think` was, stage 2 where `spells.tick` was, and stage 1 after
the fog. Within a stage, `@Behaviour(order)` then declaration order decides.

## 3. The code

### 3.1 A component and what it becomes

```java
// samples/iso-demo/src/main/java/dev/jeddy/samples/iso/Mind.java
@Component(doc = "A skeleton's state machine and timers")
public record Mind(
        MonsterState state,
        @Doc("Seconds to the next decision, path request or respawn") float timer,
        float cooldown,
        float corpse,
        Vec3f home) {}
```

The processor generates three classes beside it. `MindStore` extends `components.Store` (the
sparse set, the entity per row, growth and swap-remove) and holds the columns; an enum is an
`int` column of ordinals, a `Vec3f` is three `float` columns:

```java
// build/generated/sources/annotationProcessor/java/main/.../MindStore.java (generated)
public final class MindStore extends Store {
    int[] state;
    float[] timer;
    float[] cooldown;
    float[] corpse;
    float[] homeX, homeY, homeZ;

    static final String[] COLUMNS = {"state", "timer", "cooldown", "corpse", "home.x", "home.y", "home.z"};
    static final int[] TYPES = {INT, FLOAT, FLOAT, FLOAT, FLOAT, FLOAT, FLOAT};
    static final MonsterState[] STATE_VALUES = MonsterState.values();
    // add(entity), add(entity, Mind), get(entity), at(row), the column accessors,
    // growColumns, moveRow, resetRow, and the generic column API by name ...
}
```

`MindView` is the flyweight and `MindMut` adds the setters:

```java
// MindView.java (generated)
public class MindView extends View {
    MindStore store;

    public final void at(MindStore store, int row) {
        this.store = store;
        this.row = row;
    }

    public final MonsterState state() {
        return MindStore.STATE_VALUES[store.state[row]];
    }

    public final float timer() {
        return store.timer[row];
    }
    // ...
}

// MindMut.java (generated)
public final class MindMut extends MindView {
    public void setState(MonsterState value) {
        store.state[row] = value.ordinal();
    }
    // ...
}
```

The record is the *cold* form: `add(entity, new Mind(...))` at spawn, `get(entity)` for tools,
the editor's rows. The views are the *hot* form. The column accessors (`minds.timer()`) are for
hand-written loops: `Enemies.extractLights` and `Spells.extract` walk the columns directly, as
chapter 01 taught.

### 3.2 The store base

`Store` ([`modules/components/.../Store.java`](../../modules/components/src/main/java/dev/jeddy/components/Store.java))
owns what every store shares. `add` checks the entity is alive, appends a row (growing every
column through the generated `growColumns` when the capacity is reached — allocation, so the
registry's `CAPACITY` should cover the game) and resets the row to its defaults; `remove` is
the swap. The **generic column API** — `columnIndex(name)`, `columnType`, `getInt`/`setFloat`
and friends, `enumOrdinal(column, name)`, `assetKind(column)` — is a `switch` the processor
writes per store, and it is how the three cold paths reach a store without reflection: the level
loader, the editor and the snapshots.

### 3.3 Behaviours and the registry

A behaviour's parameters are classified by the processor:

| Parameter | Meaning |
|---|---|
| `XView`, `XMut` of a component `X` | the query: the entity must have `X`; `Mut` is a write |
| `@Optional XView` | the entity need not have it; `present()` says |
| `@Without({Y.class})` on the method | entities with `Y` are skipped |
| `float dt`, `float alpha` | the tick's or the frame's values (update phases) |
| `int entity`, `int trigger`, `int kind`, `int a`, `int b` | the entity; a trigger event's id and kind; a signal's payload |
| anything else | a **singleton** the registry takes in its constructor |

The singleton rule is what lets a behaviour reach the rest of the engine: `SkeletonAi.think`
takes `Enemies`, `Party`, `Crowd`, `Animator`, `AgentSync`, `Level`, `Rng` and `World`, so
`CryptGame`'s constructor takes those (in alphabetical order of their types), and the demo
builds the registry after them. A behaviour may also take the registry itself (`Fireballs.fly`
takes `CryptGame` to `despawn`); the processor passes `this`. No service locator, no injection
container, and a wrong type is a compile error.

The registry (`CryptGame`, under `samples/iso-demo/build/generated/sources/annotationProcessor/java/main/`
after a build) is the game's one object for all of this:

```java
// CryptGame.java (generated): the stage dispatcher
public void fixedUpdateStage(int stage, float dt) {
    this.dt = dt;
    switch (stage) {
        case 0 -> {
            SkeletonAi_think_loop();
        }
        case 1 -> {
            SkeletonAi_see_drive = Store.smaller(Store.smaller(monster, mind), sight);
            if (jobs == null) {
                SkeletonAi_see_range(0, SkeletonAi_see_drive.size(), 0);
            } else {
                fixedUpdateGroup0.setCount(SkeletonAi_see_node, SkeletonAi_see_drive.size());
                fixedUpdateGroup0.run(jobs);
            }
            SkeletonAi_show_loop();
        }
        case 2 -> {
            Fireballs_fly_loop();
        }
        default -> {}
    }
}
```

The other entry points: `update(dt, alpha)` / `updateStage`; `spawn(entity)` and
`despawn(entity)` for the lifecycle phases (`despawn` then removes every component);
`turn(entity)`; `trigger(trigger, entity, kind)` and `dispatch(events, count)` over the physics
trigger buffer; `signal(kind, entity, a, b)`; `load(level, binding)` and `loadObject`;
`write(ByteWriter, EntityIds)` / `read(ByteReader, EntityIds)`; and an accessor per store.

**Signals** are the bridge from the engine's event rings. The rules' events name creatures, the
animation events name characters; the game maps them to entities and raises a signal with a
kind it defines (`Signals.HURT`), and `@OnEvent(Signals.HURT)` behaviours run for that entity.
`Combat` drains the rules' ring as before and calls `enemies.flinch(i)`, which is now one line:
`game.signal(Signals.HURT, root[i], 0, 0)`.

### 3.4 The processor

[`ComponentProcessor`](../../tools/component-processor/src/main/java/dev/jeddy/components/processor/ComponentProcessor.java)
is a `javax.annotation.processing.AbstractProcessor`: javac calls `process` with the elements
that carry its annotations, it reads them through `javax.lang.model` (the compiler's view of
declarations, not reflection over loaded classes) and writes sources through the `Filer`. Three
things in it are worth knowing:

- **It matches annotations by name** (`dev.jeddy.components.Component` as a string), so it has
  no dependency on the runtime module: a processor that imported the annotation classes would
  need them on its own classpath and would have a version to keep in step.
- **It sees types that do not exist yet.** `SkeletonAi.think(MonsterView m, ...)` names a class
  the processor is about to generate; javac models it as an *error type* with the name as written
  and defers the "cannot find symbol" until the last round. The processor recognises
  `<Component>View` and `<Component>Mut` by their names against the records it collected, and
  the registry's own name the same way.
- **Diagnostics name the element.** Every rejected shape — a non-record, a `String` field, a
  non-static method, a `float speed` parameter, a `@Parallel` behaviour with a plain singleton —
  is reported at the record component or parameter with the reason, so the IDE underlines it.
  `ComponentProcessorTest` compiles small games through the Compiler API and checks each one.

The schema it writes, `META-INF/jeddy/components.json`, is the one description of the
components for everything outside the compiled game:

```json
{"name": "Mind", "type": "dev.jeddy.samples.iso.Mind", "doc": "A skeleton's state machine and timers", "fields": [
  {"name": "state", "type": "enum", "default": "IDLE", "values": ["IDLE", "CHASE", "ATTACK", "DEAD"]},
  {"name": "timer", "type": "float", "default": 0, "doc": "Seconds to the next decision, path request or respawn"},
  ...
  {"name": "home", "type": "vec3", "default": [0, 0, 0]}]}
```

### 3.5 Levels, the editor and the bindings

A `.jlevel` (version 2, [formats/jlevel.md](../formats/jlevel.md)) carries **component rows**:
per level object the components attached and the values set, keyed by component and column
*names*, so a renamed field does not break a level and a column left unset keeps the record's
default. `components.Levels.applyRow` turns a row into store calls through the generic column
API — `columnIndex(name)`, `setFloat`, `enumOrdinal` — and `CryptGame.load(level, binding)` runs
it for every row whose object the binding maps to an entity (`levelLoader::rootOf` in the demo),
then runs the spawn behaviours. In the editor the inspector's *Components* section reads the
schema, shows one block per row with a field per record component (sliders from `@Range`,
degrees for `@Angle`, a color picker for `@Color`, a dropdown over the level's objects for
`@EntityRef`), and every edit is a command (`ComponentRowCommand`, `SetComponentValueCommand`)
with undo and merging; a running game that attached a `ComponentSync` despawns the object's
entity and loads its rows again, so the change is live.

The cooker validates rows against the schema when it has one (`--components`, which the Gradle
plugin passes once a compile wrote the file) and generates the **bindings** (D110):

```java
// samples/iso-demo/build/generated/sources/jeddy/java/main/dev/jeddy/samples/iso/levels/CryptLevel.java
public final class CryptLevel {
    public static final String PATH = "levels/crypt.jlevel";
    /** The placement "chest". */
    public static final int PLACEMENT_CHEST = 119;
    /** The light "candles". */
    public static final int LIGHT_CANDLES = 387;
    // Repeated names, no constant: PLACEMENT_WALL, PLACEMENT_FLOOR_TILE_LARGE, SPAWN_SKELETON, ...
}
```

Only uniquely named objects get a constant — a repeated name is a prefab's, not a designer's —
and `levelLoader.rootOf(CryptLevel.PLACEMENT_CHEST)` is the entity. The bindings are not asset
outputs: the cooker lower-cases asset paths and `CryptLevel.java` must keep its case, so a
separate `generateLevelBindings` task writes them under `build/generated` before `compileJava`.

### 3.6 Snapshots

`Store.write` emits the store's name, its columns by name and type, the entity per row and the
columns into a `core.io.ByteWriter`; `read` matches columns by name, defaults the missing, skips
the unknown and refuses a changed type. The registry writes all stores and reads them by name,
skipping a store this build no longer has. Entities do not go out as handles — a handle is an
index and a generation, valid for one run of the program — but as the 64-bit **stable ids** the
game's `EntityIds` assigns (a level object by its object id, a skeleton by its spawn order, a
fireball by a counter), and an `@EntityRef` column is written the same way (its header type says
`ENTITY`, so a reader knows the column holds ids). That is M16's half of the data layer; chapter
[16](16-saves.md) has the whole save around it.

### 3.7 What stayed a singleton in the demo

`Party` and `Combat` did not become components, deliberately. The party is six fixed members
with a selection and orders — UI state, not per-entity data that varies in count; `Combat` is
the glue between the rules and the world, an orchestrator with no entities of its own. The
design says what a singleton is for: the things behaviours call, not the things that run. A
system becomes components when it has *many* entities with *the same* fields and logic; the
skeletons (300) and the fireballs (any number) did, and `Enemies` shrank to a facade that spawns
them and answers the lookups the rest of the demo had (`nearestAlive`, `enemyOf`, the soul
lights as a column loop). Skeleton $i$ is row $i$ of every store, which `Enemies.attach`
asserts: rows are added in order and never removed (a dead skeleton keeps its row and rises
again), so the old index-based code kept working.

## 4. Why it is built this way

- **Records, not classes (D105).** A record is data by construction: no behaviour to hide, a
  canonical constructor and accessors the processor can read, equality for tests, a printable
  form. The alternatives — classes with fields per entity, the dynamic `ComponentStore` of
  `scene` with named columns, reflection over record components at run time — each lose one of
  type safety, zero allocation or the editor's view.
- **Static methods, not objects (D106).** A `MonoBehaviour` is an object per entity per
  behaviour with a virtual `update()`: megamorphic calls and scattered objects, the shape §2.4
  measures. Systems as objects implementing an interface would carry state the singletons
  already hold. Static methods have nothing to construct, nothing to schedule by hand, and their
  signature *is* the query.
- **Loops and graphs from declarations (D107).** The smallest-store driver, the backwards walk,
  the hazard rule and the `JobGraph` are generated, so the author writes the body and the
  processor writes what every system would otherwise repeat; command buffers and run-time race
  detection were rejected as more machinery than the backwards rule and the static derivation.
- **One registry, singletons as parameters (D108).** The registry is the game's object; what it
  holds is decided at compile time from what the behaviours ask for. Signals keep `components`
  free of `rules`, `animation` and `physics` types.
- **Names in the file (D109).** Rows keyed by field index would break on a reordered record; a
  schema derived at run time would reflect. The JSON is written once by the compiler that knows
  the records.
- **Ids as constants (D110).** A string looked up at run time fails at run time; a constant
  fails at compile time. Entity handles cannot be constants because they exist only after load.
- **Self-describing snapshots (D111).** A hash that rejects every old save on any record change
  is the wrong default for a game in development. Entities cross a save as the game's stable ids
  (D114, chapter 16): the engine cannot know that skeleton 7 is skeleton 7 again; the game can.

## 5. Pitfalls met on the way

- **Error types.** A processor that calls `getQualifiedName()` on a parameter type that does not
  exist yet gets nothing useful; the type's *kind* is `ERROR` and `toString()` returns what was
  written. Classify by name, and only trust a `DECLARED` type's qualified name.
- **`-Werror` applies to generated code.** A `switch` expression with only a throwing default
  does not compile ("no result expressions"); a Javadoc comment before the imports is a
  dangling comment in some positions. Generate the plain forms.
- **The configuration cache.** A Gradle task's `onlyIf { extension.x.isPresent }` captures the
  build script; capture the `Property` in a local instead. CI caught it.
- **Rows move.** Anything that keeps a row index across structural changes is wrong; keep the
  entity and ask `indexOf` again. `Enemies` keeps row indices only because its stores never
  remove.
- **Lower-cased asset paths.** The cooker normalizes output paths to lower case, which is right
  for assets and wrong for `CryptLevel.java`; the bindings are a separate task, not an importer
  output.
- **A parallel behaviour is not always faster** (§2.5). Measure.

## 6. Performance

- The perf capture's new row, *Component behaviours per tick* (think, see, show, fly over 300
  skeletons): avg 0.14 / p99 0.55 ms on the job system, avg 0.11 / p99 0.51 ms inline, on the
  2-core container; the game thread stays at 0 B in the second half.
- `GeneratedGameTest.aTickAllocatesNothingInlineAndOnTheJobSystem`: 300 entities, every phase,
  inline and on two job threads, 0 bytes.
- `./gradlew :bench:jmh -Pjmh.includes=ComponentsBench`: 10,000 entities, one tick, three ways —
  `objectsWithVirtualUpdate` (an object per entity, megamorphic): 142 µs; `soaColumnsByHand`
  (the lower bound): 4.8 µs; `generatedBehaviour` (the registry through the views): 6.5 µs, on
  CI's smoke run (22 µs before the driving store's redundant lookup was removed, §2.4).
- What the registry allocates: at construction, the stores (`CAPACITY` rows each), one view per
  behaviour parameter, one set of views per job thread for each parallel behaviour, the job
  graphs. Nothing afterwards except growth past `CAPACITY`.
